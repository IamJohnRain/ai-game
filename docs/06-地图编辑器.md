# 地图编辑器 · 使用与校验标准 v1.0

> 一句话：在浏览器里**拖拽设计**一张赛图 → 实时看到结构校验与玩法审计 → 用基线脚本**试跑一局**证明它"能打起来" → 保存进地图注册表 → 在赛事里选它开打。
> 本文写给两类人：想设计新赛图的组织者，以及想知道"平台凭什么说这张图能用"的维护者。

---

## 1. 为什么要"玩法审计"，而不只是"数据校验"

早期的地图校验只有一层：`protocol.validateMap` 检查数据自洽（尺寸、镜像对称、grid 与坐标数组一致、连通性、关键设施存在）。
它保证地图**能加载**，但不保证地图**好玩**——我们真的做过一张通过全部结构校验、却被双方"守家"打成 150 回合僵尸局的图。

于是有了第二层：`engine.auditMap`。它在结构校验之上回答四个玩法问题，并把结论分成 errors（必须改）与 warnings（建议看）。

| 审计项 | 判据 | 结论 |
| --- | --- | --- |
| 尺寸 | 9×9 ~ 48×48 | 越界 → error |
| 出生点 | 不重复、可站立、两两可达 | 违反 → error |
| 出生点等价性 | 4 个出生点两两距离应完全相同（镜像对称的自然结果） | 不一致 → warning（座次会影响胜负） |
| 1v1 出生点声明 | `spawnsFor1v1` 恰好 2 个、序号合法、不是同一点 | 违反 → error |
| 设施可达性 | 每类设施（弹药/加油/资源/提交）都必须能从 1 号出生点走到 | 有不可达 → error；全部不可达 → error + "这张图打不了" |
| 设施落点 | 设施必须站在可通行地形上 | 违反 → error |
| 开局补给 | 最近弹药点/加油点 ≤ 8 步 | 超过 → warning（一开局就被压制 / 困在半路） |
| 交战压力 | 对手出生点 ≤ 6 步 → 太近；> 40 步 → 太远 | warning（开局撞脸 / 长期碰不上） |
| 掩体与遮挡 | 全图无森林 → 无隐蔽；无墙无水 → 无遮挡 | warning |
| 提交点位置 | 提交点紧贴出生点 → 搬运无风险 | warning |
| 经济正循环 | 一趟搬运净收益（`cargoMax × depositScorePerUnit − 燃油成本`）> 死亡惩罚 | 不满足 → warning（冒险搬资源不划算，双方倾向龟缩） |
| 资源可持续 | 有 `kind=center` 的高收益点；全图可持续产出 ≥ 0.3 单位/轮 | 不满足 → warning |

审计还会**实测**出一张距离参考表（从 1 号出生点出发的最短步数：到弹药点/加油点/前哨资源点/中央资源点/提交点/对手出生点，以及中央资源点到提交点），
保存地图时由服务端重算并写进地图 JSON 的 `distanceReference_P1` —— 这是组织者侧的参考资料（编辑器展示、人工审图），
**任务书已不再内联具体地图**，所以脚本不该依赖它：写进 `MAP` 的每一张图都是真跑出来的数字，但口径是"从 1 号出生点出发"。

## 2. 三条硬性设计约束（平台强制的）

1. **横竖镜像对称**。`validateMap` 要求 `grid[y][x] === grid[y][W-1-x] === grid[H-1-y][x]`。
   理由：4 个出生点必须完全等价，否则座次抽签就会影响胜负。编辑器默认开启「镜像锁定」——一笔同时改 4 个镜像格，
   天然满足；切成「自由绘制」后必须自己修对称（右侧校验面板会一直红着），或点「一键镜像化」以左上象限为准重建。
2. **设施必须可达**。任何一类设施从出生点走不到，就等于这张图有个"永远够不到的目标"。
3. **尺寸 9~48**（不要求是偶数）。取奇数时中轴线上的镜像点会与自身重合（例如 17×17 的 x=8 列），
   所以中轴线上的设施只会镜像出 2 个而不是 4 个。这不影响任何校验，只是设计时的直觉要注意。

## 3. 编辑器怎么用

| 区域 | 能做什么 |
| --- | --- |
| 左侧元素盘 | **拖**：按住元素拖到格子上放开即放置；**点**：选中画笔后在格子上按住拖动连画（一笔 = 一次撤销）。地形 4 种 + 设施 5 种 + 橡皮 |
| 中间画布 | 悬停显示坐标/地形/设施与"镜像伙伴"数量；按住拖动连续绘制；`Ctrl+Z` / `Ctrl+Shift+Z` 撤销重做 |
| 右侧面板 | 地图 id / 版本 / 一句话说明 / 尺寸 / 镜像模式 / 四周加墙 / 一键镜像化 / 清空设施 / 清空地块；导入现成地图作为起点；校验结果；统计；距离参考 |
| 出生点区 | 序号（= 脚本里 `MAP.spawns` 的顺序）、1v1 先手/后手两个下拉框、逐个删除 |
| 资源点区 | 每个资源点的类型（`home` 前哨 / `center` 中央）、容量、初始量、回复间隔，以及换算出的产出（单位/轮） |
| 车辆参数区 | 勾上才写进地图（不勾 = 整张图跟随 `RULES`）：**最大血量 / 最大载弹量 / 最大载货**。载弹量默认 5 发，**填 0 就是"禁止相互攻击"**（纯采集经济局：出门没炮弹、也装不上）；调低上限时出生与复活补给会被自动夹到上限之内 |
| 弹药点库存区 | 每个弹药点的容量（**留空 = 无限供给**，平台历史行为）、初始库存、每 N 轮 +1；填了容量就是"拿空 + 慢慢回充"，脚本能从 `state.ammoDepots[].remaining` 看到余量 |
| 加油点库存区 | 同弹药点，余量在 `state.fuelStations[].remaining` |
| 保存与试跑 | 「保存到服务端」（校验通过才可点）、「试跑一局」（不落盘，直接用当前草稿开一局基线 vs 基线）；试跑同样套用这张图的车辆参数与补给点库存 |
| 自定义地图列表 | 载入编辑 / 删除（内置地图不可删），带审计摘要（错误数/提示数） |

### 试跑给出什么

试跑用平台的**基线脚本**跑双方（`docs/examples/baseline-strategy.js`），返回：

- 交火：开火数、命中数、击杀数、**首次交火在第几轮**；
- 经济：提交单位总数、无效动作、strike；
- 逐座位比分与出生点；
- 结论列表，例如「✅ 第 4 轮就发生首次交火：地图会逼着双方碰面」「⚠️ 整局没有发生任何交火：双方的搬运路线互不接触，容易打成僵尸局」
  「❌ 双方都没有提交任何资源：得分链路是断的」。

它的意义是把"这张图设计得好不好"从嘴上的争论变成一局可复现的数据。它**不是**准入条件（保存只看审计），
但设计新图时强烈建议每次改完都跑一遍。

> 参考量级：duel-01（1v1 默认图）在 200 局仿真里 200/200 交火、首次交火平均第 4 轮、场均击杀 12.5 次。
> 如果你的新图试跑出「0 次交火」或「首次交火第 40 轮」，那它大概会变成一场龟缩局。

## 4. 保存、存储与使用

- 保存走 `POST /api/maps`：服务端用**同一套判据**再校验一遍（zod 形状 → `validateMap` → `auditMap`），
  errors 非空即拒绝（400 + 逐条错误）；通过后写入 `data/maps/<mapId>.json`（先写临时文件再改名，避免读到半份数据），
  并把 `distanceReference_P1` 按实测重算、补齐文件图例。
- 地图 id 规则：小写字母/数字/连字符，3~32 位，首尾必须是字母或数字；不能与内置地图重名（内置图 id 一律保留）。
- 服务启动时把 `data/maps/*.json` 全部读进地图注册表：**单个坏文件不会让服务起不来**，
  它会出现在 `GET /api/maps/skipped` 里（含跳过原因），前端地图列表不会展示它。
- 注册表里的地图（内置 + 自定义）会出现在三个地方：
  1. 赛事创建时的赛图下拉框；
  2. 上传校验的**逐图流水线**（所以新增一张自定义图意味着以后上传的脚本都要在这张图上跑通）；
  3. 对局记录与回放/战报里的 `mapId` / `mapVersion`（比赛用的是哪张图、哪个版本，事后可以查）。
  注意：**任务书不给具体地图**（只给尺寸范围与元素规范），所以外部 Agent 是"盲写"的——脚本必须在你这张图上也能跑通，这是有意的设计。
- 删除：`DELETE /api/maps/:id` 只对自定义地图生效；已跑过的比赛记录不受影响（对局行里存的是当时的 mapId/mapVersion）。

## 5. 命令行等价物（CI / 无浏览器场景）

```bash
# 校验内置地图 + 玩法审计（结构 + 可达性/经济/僵局风险）
pnpm cli verify-map

# 校验一个导出的草稿文件（编辑器「下载 JSON」得到的文件）
pnpm cli verify-map ./my-map.json

# 直接用草稿跑仿真（20 局，看交战与得分分布）
pnpm cli simulate --games 20 --seats 2 --map ./my-map.json

# 打印一局的逐回合轨迹（人工判断"这张图打不打得起来"）
pnpm cli inspect --map ./my-map.json --seed 20261019
```

`pnpm cli check --file strategy.js` 也会接受 `--map ./my-map.json`，用来验证某个脚本在这张新图上是否能跑通——
这正是上传闸门会对每一张注册表地图做的事。

## 6. 与外部 Agent 的关系（换图别把人家脚本弄挂）

- 任务书**不绑定地图**：它只给尺寸范围（9~64）、元素字符表与 `MAP` 结构，不给任何一张赛图的 ASCII/坐标/距离。
- 上传校验对**每一张注册表地图**各跑一遍五阶段流水线，所以自定义图越多，上传耗时略增（每张图约几十毫秒）。
  这也是"模板/参考实现里禁止硬编码坐标"的另一半原因。
- 因此：**先设计好图、跑通试跑，再宣布赛图**；如果只是试验性的图，别急着保存（试跑不需要保存）。
