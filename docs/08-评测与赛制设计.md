## 0. 为什么改：现状体检

### 0.1 现在已经测到的（不要破坏）

| 能力轴 | 现有信号 | 代码位置 |
| --- | --- | --- |
| 规格理解 / 交付纪律 | 静态禁用清单、`strategy.js` 白名单、行数上限、动作 zod schema | `packages/script-check/src/static-scan.ts`、`packages/protocol` |
| 能不能跑起来 | 沙箱编译 + 200 极端态模糊 + 30 回合冒烟 | `packages/script-check/src/index.ts` |
| 泛化（不挑图） | 任务书不给具体地图；准入对**每张注册图**各跑一遍 | `apps/server/src/routesExternal.ts`（上传循环 `registry.list()`） |
| 可复现、可审计 | 确定性引擎 + seed + 复现键 + 逐回合回放 | `packages/engine`、`packages/orchestrator` |

### 0.2 三个缺口

1. **完全没有"迭代/调试"信号**：一次性密钥，上传成功即定稿（`agents.status = 'uploaded'` 后密钥作废），模型没有"看到反馈再改"的机会，平台也观测不到它的 test-fix 行为。
2. **深度可能已经饱和在贪心**：脚本在 `onInit` 就拿到**全图**设施清单，`state` 里还免费给了所有座位分数与 `lastKnownEnemies` 记忆（`packages/engine/src/match.ts`），50ms/回合的预算对 64×64 图也过于宽松 —— 于是"路径 + 资源分配"就够了，不强依赖搜索、预测或 EV 计算。
3. **度量太粗、样本太少**：
   - 排行榜只有 6 个字段（`Store.leaderboard()`：modelId / matches / avgScore / wins / scriptOkRate / avgInvalidActions / avgStrikes），且 `avgScore` **受对手强弱影响**，不可直接比较；
   - 每对 Agent 只打 2 局、同 `pairSeed` 仅换座位（`packages/orchestrator/src/tournament.ts`），脚本又是确定性的 → **一对胜负 ≈ 1 次抽样**，换种子排名可能翻转；
   - 回合数固定 150，写死终局假设不受惩罚；
   - 已有但没上墙的高信号数据：`emergencyMoves`、`avgDecisionMs`、`disqualified`、`attempts`。

### 0.3 两项关键成本实测（本机，用于本文所有预算）

- **沙箱单局 150 回合 ≈ 67ms**（`pnpm cli simulate --games 2 --seats 2 --map duel-01 --sandbox`）。
- 上传准入：2 张图 ≈ 170ms（`apps/server/test/external.test.ts` 实测），每张图约几十毫秒（docs/06）。

> 结论：**批次化、多图、多变体的成本可以忽略**；瓶颈是"谁来判读结果"，所以本设计的重点是把结果组织成可比较的指标。

## 1. 术语与执行模型

| 术语 | 定义 | 载体 |
| --- | --- | --- |
| **批次 Cohort** | 一次评测：一组参赛 Agent + 一份 leg 计划 + 一份参赛快照 | 新表 `cohorts` |
| **轮次 Leg** | 一条 `(地图, 总回合数, 规则变体, 种子)` 组合；一个 leg = 一场现有语义的 1v1 循环赛 | 复用 `tournaments`（新增 `cohort_id`/`leg_index`/`leg_json`） |
| **标尺对局 Calibration** | 与固定参照物（`idle`、`baseline`）的对局，用来给"绝对实力"定刻度 | leg 计划里的特殊 leg |
| **练习 Practice** | 外部 Agent 用**自己的密钥**做的自测：跑准入 + 打标尺，不消耗正式提交、不计分 | 新表 `practice_runs`、`POST /api/practice` |
| **版本 Revision** | 同一 Agent 的第 N 份脚本；每份版本用**独立的一次性密钥**提交 | 新表 `agent_revisions` |

执行链：`CohortRunner`（串行编排 legs）→ `TournamentRunner`（现成）→ `runTournament`（现成）→ `runMatch`（现成）。

**不变式（重要）**

1. **快照冻结**：批次开始时把每个 Agent 解析成 `(agentId, revision, scriptSha256)` 写进 `cohorts.snapshot_json`；批次进行中新的上传**不影响**本批次的参赛脚本。
2. **leg 独立**：任何一个 leg 失败（图不存在、Agent 被删）只标记该 leg `failed`，其余继续；批次最终状态取 `finished | finished_with_errors | failed`。
3. **确定性**：`legSeed = deriveSeed(masterSeed, "cohort-leg:" + legIndex)`，`pairSeed = derivePairSeed(legSeed, aId, bId)`（复用现有实现）。同一批次用同一 `masterSeed` 可完整复现。
4. **不泄漏**：批次内没有任何通道能把对手脚本交给参赛方（见 §6.6 的练习边界）。

## 2. P0-1 多种子批次与评级

### 2.1 数据模型（全部为增量迁移，写法沿用 `Store.migrate()` 的 try/catch ALTER 风格）

```sql
CREATE TABLE IF NOT EXISTS cohorts (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  status TEXT NOT NULL,              -- pending | running | finished | finished_with_errors | failed
  master_seed INTEGER NOT NULL,
  games_per_pair INTEGER NOT NULL,
  agent_ids_json TEXT NOT NULL,
  plan_json TEXT NOT NULL,           -- leg 计划（见 2.2）
  snapshot_json TEXT NOT NULL,       -- [{agentId, revision, scriptSha256, agentName, modelName}]
  ratings_json TEXT,                 -- 评级结果（见 2.3）
  matrix_json  TEXT,                 -- 胜负矩阵
  metrics_json TEXT,                 -- 过程分画像（P0-3）
  error TEXT, created_at TEXT NOT NULL, finished_at TEXT
);
ALTER TABLE tournaments ADD COLUMN cohort_id TEXT;   -- 旧赛事为 NULL = 单场赛事，行为不变
ALTER TABLE tournaments ADD COLUMN leg_index INTEGER;
ALTER TABLE tournaments ADD COLUMN leg_json TEXT;    -- {name, mapId, maxRounds, rulesVariant}
```

### 2.2 leg 计划与默认方案

`plan_json`：

```json
{
  "gamesPerPair": 4,
  "legs": [
    { "name": "主赛 150", "mapId": "duel-01",       "maxRounds": 150, "rulesVariant": "default",   "seeds": 5 },
    { "name": "短局 60",  "mapId": "duel-01",       "maxRounds": 60,  "rulesVariant": "default",   "seeds": 3 },
    { "name": "长局 300", "mapId": "arena-01",      "maxRounds": 300, "rulesVariant": "default",   "seeds": 3 },
    { "name": "小图",     "mapId": "eval-tight-9",  "maxRounds": 150, "rulesVariant": "default",   "seeds": 3 },
    { "name": "大图",     "mapId": "eval-sprint-64","maxRounds": 200, "rulesVariant": "default",   "seeds": 3 },
    { "name": "侦察压制", "mapId": "duel-01",       "maxRounds": 150, "rulesVariant": "scout",     "seeds": 3 },
    { "name": "物流压力", "mapId": "arena-01",      "maxRounds": 150, "rulesVariant": "logistics", "seeds": 3 }
  ]
}
```

成本核对（3 个 Agent）：`3 对 × 4 局 × 7 leg = 84 局 ≈ 6s`；6 个 Agent：`15 × 4 × 7 = 420 局 ≈ 30s`。

- `seeds` 展开方式：`legIndex` 逐个自增，第 `k` 个种子 = `deriveSeed(masterSeed, "cohort-leg:" + legIndex)`；即"同一 leg 的多份种子"是**追加**的 leg（`name` 后缀 `#2`、`#3`…），保证 `leg_index` 与结果一一对应，便于按种子重跑单条 leg。
- 主赛 leg（`rulesVariant: default` + 平台默认图）是**对外可比**的正式成绩来源；其余 leg 只进入"适应力/泛化"指标（见 §4）。
- 组织者也可以只跑 1 条 leg（等价于现状），但此时评级区显示"样本不足"。

### 2.3 评级算法（Bradley–Terry MLE + bootstrap 置信区间）

输入：所有 leg 的逐局结果 `(aId, bId, winner|draw)`。

1. 统计每对的 `w_ij`（i 胜 j 的局数）、`n_ij`（总局数）。
2. MM 迭代求 BT 强度 `r_i > 0`：
   `r_i ← (wins_i + 0.5·draws_i) / Σ_j ( n_ij / (r_i + r_j) )`，迭代 100 次，每轮把 `r` 按几何均值归一（`r_i ← r_i / (Π r)^(1/N)`）。
   初值 `r_i = 1`；`Σ_j n_ij = 0` 的 Agent（未参赛/全失败）不出现在评级表。
3. 展示分值：`rating_i = 1500 + 400 · log10(r_i)`（Elo 量纲，便于人读；200 分 ≈ 10 倍强度比）。
4. **置信区间**：对"局"做 bootstrap（有放回重采样，`B = 200`），每次重算 BT，取 `rating` 的 2.5% / 97.5% 分位，报为 `rating ± CI`。
5. **样本不足规则**：某个 Agent 的参与局数 < 12 → 该行标注"样本不足（±CI 过宽）"，仍展示但排在正式榜下方。
6. 保留并同时展示：
   - `胜负矩阵 W`（i×j：胜-平-负 与净胜分差中位数）；
   - `avgScore`（原始均分，标注"受对手影响，仅供参照"）；
   - `对基线分差`（来自标尺 leg，见 §2.2/§6.1）。

实现位置：`packages/orchestrator/src/rating.ts`（纯函数，无外部依赖，便于单测）+ `apps/server/src/cohorts.ts`（编排与聚合）。

| 方法 | 路径 | 说明 |

### 2.5 前端

新增页面 **`/cohorts`（评测批次）**，并把它作为首页默认视图：

- 顶部：批次进度（`leg 3/7 · 对局 18/84`）、停止按钮；
- 主表：`名次 | Agent | 模型 | rating ± CI | 局数 | 胜-平-负 | 净胜分差 | 对基线分差 ± CI | 样本提示`；
- 矩阵热力图：行 = Agent，列 = Agent，格子 = `胜-平-负`（颜色按胜率），点开可跳该对的对局列表；
- 画像雷达/条形（§4.3）：把"纪律 / 效率 / 速度 / 鲁棒 / 适应"五轴并列展示；
- 每条 leg 折叠区：映射到现有赛事详情页（回放/战报都现成）。

### 2.6 测试（`apps/server/test/cohort.test.ts` + `packages/orchestrator/test/rating.test.ts`）

- 评级：构造已知强弱（A 全胜 B、B 全胜 C）→ 断言 `rating_A > rating_B > rating_C` 且归一化；平局各 0.5；`n=0` 不出现；bootstrap 的 CI 随局数增加而收窄。
- 批次：leg 展开条数 = `Σ seeds`；`legSeed` 可复现（同 `masterSeed` 两次展开完全一致）；`gamesPerPair` 生效；`mapId`/`rulesVariant` 非法 → 400。
- 快照：批次启动后新上传脚本**不改变**本批次参赛版本（上传后重跑同 `masterSeed` 的 leg，脚本 hash 相同）。
- 失败隔离：把某个 leg 的 `mapId` 指向已删除的自定义图 → 该 leg `failed`、其余 `finished`、批次 `finished_with_errors`。
- 兼容：旧赛事（`cohort_id IS NULL`）在列表与详情页行为不变。

### 2.7 风险与回退

| 风险 | 对策 |
| --- | --- |
| 组织者一次开太多批次把机器占满 | `AI_GAME_MAX_CONCURRENT_COHORTS`（默认 1，串行）；leg 内复用现有 `maxConcurrentMatches` 上限 |
| BT 在"全胜/全败"极端矩阵下不收敛 | Laurent 正则：`r_i ← (wins_i + 0.5·draws_i + ε) / (Σ ... + ε)`，`ε = 0.1`；单测覆盖"某 Agent 全败" |
| 与现有"赛事"页概念重复 | 保留赛事页（单场赛事 = 1 leg 批次），批次页只做汇总与评级；两者共用 `/api/matches/:id/replay|report` |

## 3. P0-2 混合回合数（短局 / 标准局 / 长局）

**现状**：`RULES.maxRounds = 150` 已是**每局参数**（`TournamentInput.maxRounds`，10~1000；`TournamentRunner` 把它覆盖进 `Ruleset` 传给引擎），引擎把它原样给脚本（`RULES` 全局 + `match_start.rules`）。所以**不需要改引擎**，只需要真的用起来 + 在任务书里说清楚。

**做法**

1. leg 计划里混 `maxRounds: 60 / 150 / 300`（§2.2 已含）。
2. 任务书（`docs/prompts/task-doc.template.md`）§5.3 与 §6.5 增加一句：
   > 总回合数由赛事指定（会有 60~300 回合的短局/长局混排），用 `RULES.maxRounds` 与 `state.round` 推算剩余回合；**不要写死 150**，也不要把"最后几回合怎么收尾"写死成固定回合号。
   同时 §7 数值表下方注明：**表内是默认值（ruleset-1.1），赛事可覆盖其中可调项**（回合数、参数变体），一切以运行时 `RULES` 为准。
3. 新增指标 **终局利用率** = 最后 20% 回合内的提交单位 / 总提交单位（从 `match_replays` 事件流离线计算，供画像使用）。它会直接区分"会做终局估值"的脚本与"匀速刷分"的脚本。

**测试**：`maxRounds=60` 的对局确实在第 60 回合结束、脚本读到的 `RULES.maxRounds` 是 60（在 smoke 里断言）；任务书渲染后包含"总回合数由赛事指定"。

## 4. P0-3 过程分与能力画像（指标字典）

### 4.1 指标定义（每条给出公式与数据来源）

| 指标 | 公式 | 数据来源 | 现状 |
| --- | --- | --- | --- |
| 一次通过率 | 上传成功且 `attempts_at_upload = 0` 的 Agent 占比 | `agents`（**新增列 `attempts_at_upload`**） | 部分（现只有 `status`） |

| 改进斜率 | 见 §7.4 | `agent_revisions` + 标尺分 | 无 |
| 对抗评级 | `rating ± CI`（§2.3） | `cohorts.ratings_json` | 无 |
| 对基线分差 | 与 `baseline` 标尺的平均分差 ± CI | 标尺 leg | 无 |

### 4.3 五轴归并（给非技术读者的一屏结论）

| 轴 | 组成 | 含义 |
| --- | --- | --- |
| 可运行性 | 一次通过率、准入各阶段失败率 | 写得出能跑的代码吗 |
| 纪律 | AP 利用率、应急移动率、DQ 率 | 动作有没有想清楚再发 |
| 效率 | 每百回合提交、补给占比、终局利用率 | 同样的时间能赚多少分 |
| 速度 | avg / max 决策耗时 | 复杂度控制 |
| 对抗 | rating ± CI、对基线分差 | 真打起来强不强 |
| 适应 | 各 leg 得分的离散度（图/回合数/变体之间） | 换环境还行不行 |

展示：批次页每行展开即见五轴小条；`/report` 里给 Markdown 表格（便于贴到评测报告里）。

**测试**：构造一份手写的 `stats_json` 与 `match_replays`，断言每个公式的结果（含除零保护）；断言排行榜旧字段值不变。

## 5. P0-4 考察图池与规则变体

### 5.1 考察图（5 张，作为"难度阶梯"存在）

放在仓库 `maps/eval/*.json`，由 `deploy/install.sh` 复制到 `$APP_DIR/data/maps/`（= 自定义地图，`MapRegistry` 会自动加载并审计；id 需满足 `CUSTOM_MAP_ID_RE`，且不与内置图冲突）。

| id | 尺寸 | 设计意图 | 关键验收 |
| --- | --- | --- | --- |
| `eval-tight-9` | 9×9 | 极小图：出生点相邻、唯一提交点居中、无森林 → 逼纯规划，惩罚"长程假设" | `auditMap` 无 errors；`spawn_to_deposit ≥ 3` |
| `eval-sprint-64` | 64×64 | 大图：资源点少且远离出生点 → 逼燃油预算与长程路径 | 一趟补给往返 ≥ 30 步 |
| `eval-maze-33` | 33×33 | 窄道/死角多：资源点在死角 → 逼 `pathFind` 失败兜底与改道 | 至少 3 个资源点 `pathFind` 需绕行 ≥ 2 倍直线距离 |
| `eval-camp-15` | 15×15 | 提交点贴出生点、资源点全在中央 → 放大"蹲守 vs 搬运"的收益权衡（EV 计算） | `spawn_to_deposit ≤ 2`、`spawn_to_centerResourceNode ≥ 4` |
| `eval-fortress-24` | 24×24 | 森林密集：视野受限、盲射与偷袭 | 森林占比 ≥ 25%、`visionRadius` 6 下全图可见率 < 40% |

共同约束（否则加载即被拒）：9~64 格、**水平与垂直镜像对称**、全图连通、出生点 ≥ 2、弹药/加油/资源/提交点各 ≥ 1。
验收命令：`pnpm cli verify-map maps/eval/*.json`（结构 + 玩法审计 + 距离表）。

**为什么这就够了**：注册表里的每一张图都会进准入（`registry.list()`），所以"加一张难图"= 给**所有未来上传**加一道新门槛，零额外机制成本。

**成本核对**：上传准入从 2 张图（~170ms）增至 7 张图（~500ms 量级，实测后再定）；若超过 1s，退路是把"考察图"拆成**软门槛**：仍跑，但失败只在 `validation[]` 里标红 + 报告中列出（不进 `firstFailure`），由组织者决定是否放行。

### 5.2 规则变体（数据，不改引擎）

新增 `packages/protocol/src/rules-variants.ts`：

```ts
export const RULES_VARIANTS: Record<string, Ruleset> = {
  default: DEFAULT_RULESET,
  // 侦察压制：视野砍半、森林更隐蔽、记忆不再免费给（考验"自己攒情报"）
  scout: { ...DEFAULT_RULESET, version: "1.1-scout", visionRadius: 3, forestStealthRadius: 4, lastKnownMemoryRounds: 0 },
  // 物流压力：油箱更小、耗油更高、应急燃料更贵（考验补给规划）
  logistics: { ...DEFAULT_RULESET, version: "1.1-logistics", fuelMax: 60, moveFuelCost: 3, emergencyMoveCost: 4 },
};
```

- 已核实：`visionRadius`、`forestStealthRadius`、`lastKnownMemoryRounds`、`fuelMax`、`moveFuelCost`、`emergencyMoveCost` 在引擎里**全部运行时读 `RULES`**（`packages/engine/src/match.ts`），因此变体是纯数据。
- 记录方式：`matches.ruleset_version` / `tournaments.ruleset_version` 已存在 → 变体名字直接落库，成绩可归因；批次 leg 再带一份 `rulesVariant`。
- **版本号策略**：变体不改脚本契约（脚本本来就必须读 `RULES`），所以 `SCRIPT_PROTOCOL_VERSION` 仍为 `p1.0`；但**榜单必须按 `rulesetVersion` 分组展示**，不得与 default 混排。任务书 §7 加一句"赛事可能使用参数变体，一切以运行时 `RULES` 为准"。

### 5.3 测试与风险

- `verify-map` 对 5 张考察图全绿（纳入 `pnpm verify`）。
- 变体：用 `scout` 跑一局，断言脚本看到的 `RULES.visionRadius === 3`、`match_start.rules.rulesetVersion === "1.1-scout"`。
- 风险：**收严门槛会筛掉已有脚本**（原先只在 2 张图通过）。对策与时间表：先在**新批次**里启用考察图，用报告展示"哪些脚本会在新门槛下失败"，一个批次之后正式生效；README/任务书同步更新"准入覆盖全部注册图"的措辞。

## 6. P1-5 练习通道（dry-run）

### 6.1 语义与不变式

外部 Agent 在执行过程中需要"能自测"，但现有链路只有一次正式提交。练习通道把自测变成**可观测**的：能测、能改，但不影响成绩。

**必须成立的不变式**

1. 练习**不消耗**正式密钥：不触发 `markAgentUploaded`、不改 `status`、不加 `attempts`。
2. 练习**不计入**任何成绩：不建 `matches` 行（或建但标 `practice=1` 且被所有统计排除——采用前者，避免污染回放/排行榜）。
3. 练习对手**只有标尺**：`idle`（挂机）与 `baseline`（平台基线，公开在仓库里）。**永远不与其它参赛 Agent 对局**，避免"用练习摸对手"。
4. 配额与限流：每 Agent 默认 5 次（`AI_GAME_PRACTICE_RUNS`），按来源 IP 复用 `auth.ts` 的限流器。
5. `status = 'uploaded'` 之后不允许练习（409），防"上传后继续探测环境变量/规则"。

### 6.2 数据模型

```sql
CREATE TABLE IF NOT EXISTS practice_runs (
  id TEXT PRIMARY KEY, agent_id TEXT NOT NULL, created_at TEXT NOT NULL,
  ok INTEGER NOT NULL, stage TEXT, detail TEXT,
  stages_json TEXT, practice_json TEXT,          -- 逐阶段结论 + 标尺局结果
  source_ip TEXT
);
ALTER TABLE agents ADD COLUMN practice_runs INTEGER NOT NULL DEFAULT 0;
ALTER TABLE agents ADD COLUMN max_practice_runs INTEGER NOT NULL DEFAULT 5;
```

### 6.3 API 契约

```
POST /api/practice
  Authorization: Bearer <该 Agent 的密钥>      # 与上传同一把，但练习不消费它
  Content-Type: application/zip
  body: 原始 zip 字节流（同样的 200KB / 白名单 / 防炸弹闸门）

→ 200 {
    ok: true,
    validation: [{ stage, mapId, ok, detail }],
    validatedMaps: ["duel-01", "arena-01", ...],
    practice: {
      rounds: 60, mapId: "duel-01", seed: 20261019,
      opponents: [
        { kind: "idle",     myScore: 210, oppScore: 12, result: "win",
          my: { unitsDeposited: 22, deposits: 5, invalidActions: 0, strikes: 0, avgDecisionMs: 0.7, kills: 0, deaths: 0 } },
        { kind: "baseline", myScore: 132, oppScore: 166, result: "loss", my: { ... } }
      ]
    },
    quota: { used: 2, max: 5 }
  }
→ 4xx { ok: false, stage: "auth|zip|content|static|compile|fuzz|smoke|quota", error, validation? }
```

- 练习局固定 60 回合、固定 seed、平台默认图，保证**同一脚本的多次练习可比**。
- 复用现成实现：`checkScript()`（五阶段）+ 两次 `runMatch`（vs 挂机脚本、vs `docs/examples/baseline-strategy.js`）。
- 也允许只跑准入不跑对局：`?dryRun=validation`（更省时，用于快速定位失败阶段）。

### 6.4 成本与限流

每次练习 ≈ 准入（7 张图 ≈ 0.5s）+ 2 局×60 回合（≈ 0.05s）≈ **0.6s**；每 Agent 上限 5 次，10 个 Agent 的批次总开销 < 30s，可忽略。

### 6.5 得到的指标（这才是这条通道的真正目的）

| 指标 | 定义 | 说明 |
| --- | --- | --- |
| 自测次数 | `agents.practice_runs` | 有没有"先测再交"的习惯 |
| 首次自测通过率 | 第 1 次练习就 `ok` 的比例 | 一次写对的概率 |
| 修复迭代数 | 从第 1 次失败到最终上传成功的练习次数 | test-fix 效率 |
| 练习失败阶段分布 | `stage` 直方图 | 常见错在哪（静态扫描 / 编译 / 模糊 / 冒烟） |
| 标尺分 | vs `idle` / `baseline` 的得分 | 版本之间的**绝对刻度**，支撑 §7.4 的改进斜率 |

### 6.6 文档与测试

- 任务书 §2（注册与密钥表）新增一行"练习通道"，§9 增加"练习阶段的返回与你该改什么"，§11 自查清单第 10 条改为"先用练习通道跑通（配额 N 次），再提交正式版本"。
- 测试：密钥不消费（`status`/`attempts` 不变）、配额耗尽 429、`status=uploaded` 时 409、练习不建 `matches` 行、失败不计入 `attempts`、响应形状与统计正确。

## 7. P1-6 版本化提交与改进斜率

### 7.1 语义与不变式

- 同一 Agent 可以有 `N` 个**版本**；**每个版本用一把新的一次性密钥**（沿用现有"重新签发"流程：`POST /api/agents/:id/reissue`），所以"一轮 = 一把密钥"的组织方式不变，防重复提交的性质不变。
- 版本上限 `AI_GAME_MAX_REVISIONS`（默认 3）。
- 批次启动时**冻结**每个 Agent 的版本（`snapshot_json`），批次中途上传不影响它。
- 解析策略 `revisionPolicy`：`latest`（默认，取批次开始时最新版本）| `best`（取标尺分最高的一版）| `pinned`（组织者指定版本号）。

### 7.2 数据模型

```sql
CREATE TABLE IF NOT EXISTS agent_revisions (
  id TEXT PRIMARY KEY, agent_id TEXT NOT NULL, revision INTEGER NOT NULL,
  script TEXT NOT NULL, script_sha256 TEXT NOT NULL, zip_sha256 TEXT, zip_bytes INTEGER,
  meta_json TEXT, validation_json TEXT, attempts_at_upload INTEGER NOT NULL DEFAULT 0,
  source_ip TEXT, uploaded_at TEXT NOT NULL,
  UNIQUE (agent_id, revision)
);
ALTER TABLE agents ADD COLUMN revision INTEGER NOT NULL DEFAULT 0;      -- 0 = 还没有任何版本
ALTER TABLE match_players ADD COLUMN revision INTEGER;                  -- 成绩按版本归因
```

`POST /api/upload` 契约追加：成功响应多一个 `revision`；`agents` 的当前脚本字段继续指向**最新版本**（兼容现有读者），历史在 `agent_revisions`。

### 7.3 版本与批次的交互

- `POST /api/cohorts` 的 `snapshot_json` 记录 `revision` 与 `scriptSha256`；`GET /api/cohorts/:id` 显示"本批次用的是 v2"。
- 组织者发起下一轮：UI 上「为下一轮签发密钥」按钮（内部调 `reissue` + 返回新的启动 prompt，§上一版功能），Agent 交新版 → `revision + 1`。

### 7.4 改进斜率（新指标）

- 每个版本的**标尺分**：来自该版本的练习局（§6.5，同 seed/同图/同回合数，可比）；没有练习记录时回落到批次里的标尺 leg。
- 定义：
  - `版本数 versionCount = N`
  - `净改进 Δscore = score_vN − score_v1`（标尺分）
  - `改进斜率 = Δscore / (N − 1)`（`N = 1` 时标注"未迭代"）
  - `首个达标版本`：第一次通过准入的版本号（区分"一开始就能跑"与"改了几版才跑通"）
- 展示：批次页每行给 `v1→vN` 的小折线（标尺分），以及"每版之间改了什么"的备注（`meta.json` 的 `note` 字段，已在包里支持）。

### 7.5 测试与风险

- 版本：`revision` 自增、`UNIQUE(agent_id, revision)`、超过上限 409、每版独立密钥（旧密钥废）、`latest/best/pinned` 三种解析、快照冻结。
- 风险：组织者工作量上升（每轮要签发密钥）→ 用 UI 一键按钮 + 启动 prompt 一并给出；报告中标注"本批次版本 v2，共迭代 2 次"。

| P1-5 练习通道 | `POST /api/practice`：完整五阶段 + 两局固定 60 回合标尺对局；不消耗密钥、不计分、只打标尺、配额 429；产出"自测行为"指标 | `apps/server/src/practice.ts`、`practice_runs` 表、6 项验收测试 |
| P1-6 版本化提交 | `agent_revisions` + `agents.revision`；每版一把一次性密钥；`latest/best/pinned`；批次快照冻结；`match_players.revision` 归因 | `store.ts::markAgentUploaded/listAgentRevisions/agentScriptAtRevision`、`routesCohorts.ts::pickBestRevision` |

**与设计稿的偏差（都是实现时的取舍，功能等价或更简单）**

1. **leg 计划默认值更小**：主赛 3 个种子、其余 2 个（设计里写 5/3/3/3/3 + 每张考察图 3）——因为加了 2 个标尺对手后参与人数从 3 变 5，配对数是 C(5,2)=10，原计划会让单批对局数翻几倍。实测：3 个参赛者跑默认计划 ≈ 60~90s。
2. **标尺对手是"参与者"而不是单独的 calibration leg**：idle/baseline 直接进循环赛（`model_id = calibration`，榜上单列并标"标尺"），这样评级天然带刻度，不需要额外的对照赛机制。代价是它们会占一对位置。
3. **终局利用率用 `turn_begin` 事件推回合号**：引擎的 `deposit` 事件不带 `round`（协议如此），所以按事件流里的回合号统计"最后 20% 回合"的提交占比。
4. **`best` 策略的判据是"该版的标尺分"**：练习记录发生在上传之前，所以第 N 版的练习 = 上一次上传之后、这次上传之前的那些练习局；没有练习数据时回落到 `latest`（并在快照里标 `latest-fallback`，不假装自己是 best）。
5. **scout 变体的 `lastKnownMemoryRounds: 0`**：原 `RulesetSchema` 要求正数，已放宽为 `nonnegative`（0 = 记忆只在当前回合有效），并加测试保证所有变体都过 schema。
6. **并发上限用 `AI_GAME_MAX_CONCURRENT_COHORTS`（默认 1）**：只统计"正在跑"的批次；跑完的 runner 留在内存里供前端看结果，不占并发位。
7. **线上实测暴露并修掉的两个问题**（都补了回归测试）：
   - **事件循环被堵**：`runTournament` 的对局循环原本不让出宏任务，一次 600 局批次会把 HTTP 请求整体阻塞（实测 `POST /api/cohorts` 251s 才返回、进度轮询直接 ECONNRESET）。现在每局后 `setImmediate` 让出事件循环，发起请求立刻返回。
   - **练习通道漏了免登录白名单**：`auth.ts` 的 `PUBLIC_ROUTES` 只加了 upload 没加 practice，线上直接 401；而单测此前用“带会话 Cookie”的 helper 打接口，把这个问题掩盖了 —— 现已改成裸 `app.inject`（不带 Cookie）来验证“免登录”这一属性本身。
   - 顺带收紧：默认 leg 计划的种子数按参与人数缩放（6 人时 Σseeds 21 → 11），并加单批局数上限 `AI_GAME_MAX_COHORT_MATCHES`（默认 1200），避免一次点出上千局。
   - **补给占比在零产出局上爆炸**（上线后看真实数据才发现的指标问题）：分母用 `MAX(1, 得分)` 时，一局没提交也没击杀的对局会把 24 点油费算成“114 倍”，976 局聚合出 3.25（中位数才 0.21）。改为**只在有产出的对局上求比值**，并新增**无产出局占比**把这类局单独暴露出来（它本身也是“打得毫无产出”的信号）；排行榜/批次页并排显示为 `0.36（无产出 4%）`。
8. **实测性能**（线上 2G 小机器）：沙箱单局 150 回合约 0.4s（开发机 0.07s）；含 9 张注册图的准入（= 上传/练习一次的校验）约 2.7s——单次上传可接受，未触发“考察图改软门槛”的退路。
9. **UI 默认页没有变**：新增「评测批次」导航项，但首页仍是「Agent 自助接入」（设计稿里写的"作为首页默认视图"没做，避免改变既有习惯）。

## 13. 边界（本设计明确不做）

1. **不改玩法机制**：不加单位、不改经济数值、不移除 `lastKnownEnemies`（这些属于"提升算法深度"的第二期，见 §0.2 缺口 2 的备选方案，需另立设计并升协议版本）。
2. **不做实时/在线对局**：批次仍是批量跑完再看，保持确定性可复现。
3. **不做跨模型自动挑选最优版本**：改进斜率只报告事实，选择权在组织者。
4. **不让参赛方看到对手脚本或对手的练习结果**：批次的可见性规则与现有赛事一致。
