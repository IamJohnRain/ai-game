## 2. 怎么跑

```bash
pnpm install

# 1) 自检（地图结构 + 玩法审计 + 文档一致性）
pnpm verify

# 2) 外部 Agent 流程自测（外部 Agent 只需要这三条）
pnpm cli task-doc --out task-doc.md                    # 生成任务书（与地图无关）
pnpm cli pack --file strategy.js --out strategy.zip    # 打包并自查解包
pnpm cli check --file strategy.js                      # 走一遍准入流水线（对每张注册表地图各跑一遍）

# 3) 平衡性仿真（不调模型，直接跑脚本；地图默认随人数：2 人→duel-01，3~4 人→arena-01）
pnpm cli simulate --games 200 --seats 2                # 1v1 决斗图：看交战强度与得分分布
pnpm cli simulate --games 60 --seats 4                 # 四方局
pnpm cli simulate --games 10 --seats 2 --sandbox       # 沙箱执行（与正式对局同口径）
pnpm cli inspect --seed 20261019                       # 打印一局的逐回合轨迹（人工判断地图是否打得起来）
pnpm cli simulate --games 20 --seats 2 --map ./my-map.json   # 直接仿真还没保存的自定义地图草稿

# 4) 一键演示数据（注册 3 个 Agent → 打包上传 → 跑一场 1v1 赛事；可随时在网页上删除）
pnpm cli demo

# 5) 启动平台
pnpm dev:server        # http://127.0.0.1:8787 （REST + WS）
pnpm dev:web           # http://127.0.0.1:5173 （已配置 /api 与 /ws 代理）
pnpm build:web         # 构建后由 server 直接托管：访问 http://127.0.0.1:8787
```

前端脚本走 `pnpm --filter @ai-game/web dev`（即 `pnpm dev:web`）。**不要用 `npx vite`**：那会去 npx 缓存里拉一个新版本 Vite，
和仓库锁定的 6.4.4 不是同一份（`apps/web/node_modules/.bin/vite` 才是锁定的那份）。

环境变量：`PORT`、`AI_GAME_DATA_DIR`、`AI_GAME_MASTER_KEY`（32 字节 hex/base64，缺省会在数据目录生成开发密钥）、
`AI_GAME_TURN_INTERVAL_MS`（观战节奏）、`AI_GAME_PUBLIC_URL`（对外基础地址，给外部 Agent 用的 URL 一律以它为准）。

## 5. 已知限制 / 待办

1. **登录是单账号**：用户名固定 `JohnRyan`，密码**不内置**（`.env` 的 `AI_GAME_AUTH_PASSWORD`，或未配置时首次启动
   随机生成到 `data/auth.password`；仓库里翻不到任何密码），会话存服务端内存（重启即全部登出，默认 7 天过期）。
   除任务书与上传外，页面/接口/WebSocket 都要会话；上传接口先验密钥再收文件。
   这挡住了"路人随手乱点"，但**不是多用户体系**：没有按 owner 过滤查询、没有角色/审计日志。
   表结构里的 `owner_id` 列仍是为此预留的。
2. **前端迷雾判定去重**：把 `visibleBy` / 记忆过期逻辑从 `apps/web` 挪回 `packages/engine` 导出，避免两边口径漂移。
3. **对局并发**：赛事在服务进程内串行跑（QuickJS 沙箱 + 异步）。设计文档里的 `worker_thread` 版本尚未实现；单机 4 并发实测无压力。
4. **地图编辑器的协作**：没有版本历史与"草稿共享"，只有"保存即生效"；多人同时编辑同一张图会互相覆盖。
5. **排行榜**：按模型名聚合平均分/胜场/脚本通过率；ELO 需要多局两两对阵数据，留待有真实比赛量后加。
6. **赛事赛制单一**：只做单循环 1v1（`gamesPerPair` 默认 2）；淘汰赛/分组/团队赛需要新的赛程生成器，引擎与落库层可直接复用。
7. **上传只接受原始 zip 字节流**：不支持 multipart；对外文档与 CLI 已给出 curl 示例。
8. **`combat` 观测口径**：CLI 的"交火局数/首次交火轮次"是从事件流现算的（`fire` 事件 + `turn_begin`），没有单独的埋点表。

## 6. 关键安全边界（已实现）

- **上传内容永远当数据**：zip 只用中央目录做白名单判定、**不递归解压**（结构上排除解压炸弹/死循环/路径穿越），
  单条与总量双上限（声明尺寸撒谎也会被拦）；脚本在 QuickJS 沙箱编译执行，主进程从不 `eval` 上传文本。
- 沙箱内无网络/无文件/无 `Date`/无 `Math.random`/无 `eval`/无 `Function`；唯一宿主桥是 `__hostApi(name, json)`，只传 JSON 值。
- `onTurn` 50ms + 64MB、`onInit` 1000ms + 256MB 硬预算；超时/内存溢出后该沙箱停用（连续 3 次 strike 淘汰座位，对局不中断）。
- **一次性密钥**：只显示一次，库里只存 `sha256(masterKey || key)`，固定时间比较，尝试次数上限，成功后立即失效；
  上传成功/失败都在 `agents.attempts` 留痕。
- **地图是不可信输入**（虽然目前只有本地编辑）：zod 形状 → `validateMap` 结构 → `auditMap` 玩法 → 重算距离表 → 原子落盘；
  启动时坏文件跳过并记因，不会让服务起不来。
- 复现能力：`reproducibilityKey = sha256(脚本协议版本 + 规则版本 + 地图版本 + 种子 + 各座位脚本哈希)`，同键重跑事件流逐字节一致（引擎测试覆盖）。
