# 坦克对战平台 · 游戏规则 v1.2（ruleset-1.2）

> 这份文档是**唯一数值权威**。引擎实现、任务书、前端展示、战报结算都必须与本文一致。
> 版本号：`ruleset-1.2`。任何数值/机制修改 → 升版本号 → 旧比赛按旧版本回放，排行榜分版本统计。

---

## 1. 对局形态

| 项目 | 取值 | 说明 |
| --- | --- | --- |
| 参战 AI 数量 | 2 ~ 4 | 2 人即 1v1，默认地图 `duel-01`（南北对峙出生点）；3~4 人默认地图 `arena-01` |
| 赛制 | 回合制（每轮每个 AI 各行动一次） | 座位顺序每轮轮换起始位，避免先手优势 |
| 默认回合数 | `maxRounds = 150` | 每轮 = 每个存活座舱各被调用一次脚本 |
| 胜负 | 结束后总分最高者胜 | 平局判定见 §7 |
| 观战节奏 | 默认 1200ms/回合，可 1x/2x/4x/8x/极速 | 极速先跑完，再由前端回放 |

**"每轮每个 AI 一个轮次"**：第 `r` 轮的行动顺序为 `[((r-1) mod N)+1, ...]` 循环展开，即每轮第一个行动的座位向后轮换一位。公开信息（`state.turnOrder`）。

**先后手公平性**：地图为镜像对称（见 §2），座次在开赛前由种子随机抽签决定，抽签结果写入战报。2 人局用地图自己声明的 `spawnsFor1v1`（arena-01 取对角两点，duel-01 取南北对峙两点），3~4 人局用 `SPAWN_SETS`。

**"能打起来"是这张图的硬指标**（实测见 §9）：

1. **唯一提交点在正中央**——想把这局的分变成比分，就必须站上那一格；两个资源点是它的左右邻居，等于在同一个格子里抢钱。
2. **出生点离中央只有 6 步**（3 回合），视野 6 格、射程 8 格，双方第 3~4 回合必然照面（实测首次交火平均第 4 回合；arena-01 是第 10 回合）。
3. **补给线路短**：弹药在出生点旁 2 步、加油点在通道上，所以"打空了要回一趟"的成本很低，交火能持续进行而不是打两发就散。
4. **四角前哨资源点产出只有中央的 1/4**，苟在角落等回充是稳输的下策（实测保守流派平均 122.9 分 vs 争夺中央 265.4 分）。

### 2.3 地图还能改什么（地图级参数）

除了地形与设施布局，地图 JSON 还能带两块**改数值**的字段 —— 编辑器里对应「车辆参数」「弹药点库存」「加油点库存」三个面板：

**① `tuning`：车辆上限（可只写要改的项）**

| 字段 | 含义 |
| --- | --- |
| `hpMax` | 血量上限（默认 100） |
| `ammoMax` | **载弹上限**（默认 20；编辑器的默认档是 5 发）。**`0` = 禁止相互攻击**——装不了弹就打不出去，那张图只能靠采集与提交比高低（但地雷仍可击杀，想彻底没战斗要把 `mineMax` 也写 0） |
| `cargoMax` | 载货上限（默认 5；`0` = 采了也装不下，得分只能来自击杀） |
| `mineMax` | **随身地雷上限**（默认 2；`0` = 这张图没有地雷，`deployMine` 永远记 `NO_MINE`） |

上限调低时，**出生与复活的补给会被自动夹到上限之内**（例如 `ammoMax: 0` 的图上坦克出门就没有炮弹）。引擎内部只认"有效规则"，所以地图参数不改变任何引擎代码路径，`match_start` 事件里记录的也是合并后的数值。

**② 补给点库存：`ammoDepots` / `fuelStations` 里每个点可以带容量**

| 地图里的形状 | 行为 |
| --- | --- |
| `{"x": 5, "y": 2}` | **无限供给**（平台历史行为）：站在上面、分数够就能一直补给 |
| `{"x": 5, "y": 2, "capacity": 12, "initial": 6, "regenEveryRounds": 3}` | **有库存**：开局 6 发，每 3 轮回 1 发、封顶 12 发；拿空后 `loadAmmo` 被拒（`AMMO_EMPTY`），得等回充 |

校验器会拦下"写了容量却没说刷新间隔""初始量超过容量""只写了初始量却没写容量"这三类半截配置；审计器会提示"只有部分补给点写了容量，玩家会绕远去无限的那些""容量不够一次补给""总回复过低"。

脚本侧看到的是 `state.ammoDepots[].remaining` / `state.fuelStations[].remaining`（`capacity: null` = 无限供给，`remaining: null` = 不在视野里）。

## 3. 坦克属性

| 属性 | 上限 | 初始值（开局 / 复活） |
| --- | --- | --- |
| 结构值 HP | 100 | 100 |
| 弹药 ammo | 20 发 | 6 发（复活同） |
| 燃油 fuel | 100 | 40（复活同） |
| 载货 cargo | 5 单位 | 0 |
| 地雷 mines | 2 枚 | 2 枚（复活同，满装） |

上表是规则默认值（ruleset-1.2）。**地图可以用 `tuning` 覆盖 HP / 弹药 / 载货 / 地雷四项上限**（§2.3）：覆盖时出生与复活的补给会被夹到新上限之内。

- 同一格不能同时存在两辆坦克（不可穿越、不可叠放）。
- 没有"修理"机制：HP 只能通过死亡复活回满（死亡代价见 §6）。
- 死亡时载货全部损失。

## 4. 回合与动作（AP）

每辆坦克每个回合拥有 **2 点行动力 AP**，脚本返回**最多 2 个动作**，按数组顺序依次执行；AP 用尽或动作执行完即结束本回合，未用完的 AP 不累积。
**AP 是按动作扣的**：`wait` 不花 AP、`defend` 花整回合（2 点）、其余动作各 1 点。所以"防御 + 别的动作"同回合返回时，排在后面的那个动作会因为 AP 不够而记为 `NO_AP` 无效动作（防御本身照样立起来）；反过来 `[移动, 防御]` 里的防御立不起来。

| 动作 | 前置条件 | 消耗 | 效果 |
| --- | --- | --- | --- |
| `{type:"move", dir}` | 燃油 ≥2、目标格可通行且无坦克 | 1 AP + 2 燃油 | 移动 1 格（落脚点若有地雷 → 立刻引爆，见 §5） |
| `{type:"fire", target:{x,y}}` | 弹药 ≥1、目标格距离 ≤8、有视线 | 1 AP + 1 发 | 按 §5 结算命中与伤害（目标在防御中则伤害全免） |
| `{type:"collect"}` | 站在资源点上且 `remaining ≥ 1`、未满载 | 1 AP | 采集 `min(3, remaining, 载货空余)` 单位入舱 |
| `{type:"deposit"}` | 站在提交点且载货 ≥1 | 1 AP | 载货清零，**+10 分/单位** |
| `{type:"loadAmmo"}` | 站在弹药补给点、弹药或地雷未满，且该点还有库存（无限供给的点恒成立） | 1 AP | 装填 `min(6, 弹药空余, 该点余量)` 发、**扣 2 分/发**；同时把地雷补满到上限（**不额外扣分**，也与弹药共享该点库存） |
| `{type:"refuel"}` | 站在加油点、燃油未满，且该点还有库存 | 1 AP | 加入 `min(30, 燃油空余, 该点余量)`，**扣 1 分/10 燃油（按实际加入量向上取整）** |
| `{type:"defend"}` | 无（整回合不做别的事） | **2 AP（= 整回合）** | 停止一个回合举盾：立刻生效，**2 轮内炮弹伤害全免**（见 §5） |
| `{type:"deployMine"}` | 随身地雷 ≥1、所在格可通行 | 1 AP + 1 枚地雷 | 在**自己当前所在的格子**埋一枚地雷（不分敌我、对所有人不可见，见 §5） |
| `{type:"wait"}` | 无 | 0 AP | 空动作（占位，便于脚本清晰表达） |

**无效动作规则**（关键，脚本必须自查）：
- 不满足前置条件（撞墙、撞车、燃油不足以支付移动、无弹药射击、超射程、无视线、站在非补给点补给、没有地雷可布（`NO_MINE`）、本回合 AP 已经花光（`NO_AP`）……）→ 该动作**消耗 1 AP 但无任何效果**，同时引擎记录一条 `invalid_action` 事件并计入该座位的 `invalidActions` 统计。
- 无效动作**不扣燃油/弹药/分数**（没有发生的事不收费），但浪费的 AP 本身就是惩罚。
- 返回超过 2 个动作 → 只执行前 2 个，多余丢弃并记一条事件。
- 返回非数组 / 元素结构非法 → 整个回合视为无动作，记 `invalid_action`。

## 5. 视野与战斗

**视野（每个回合开始时计算，引擎直接给出结果）**
- 视野半径 **6 格（切比雪夫距离，即国王步数）**。
- 视线（LOS）判定：`#` 墙与 `f` 森林阻挡视线（目标格自身不算阻挡）；`~` 水不阻挡视线。可用 `API.hasLOS(a,b)` 自查。
- 站在森林中的坦克属于隐蔽状态：**只有距离 ≤3 格时才可能被看到**。
- 引擎在 `state` 中直接给出结果：`state.enemies`（当前可见敌人，含精确坐标与 HP）、`state.lastKnownEnemies`（引擎维护的短期记忆，保留 12 轮回溯）。资源点的剩余量只有在视野内才给出数值，否则为 `null`。

**射击**
- 射程 ≤ **8 格**（切比雪夫距离），必须有 LOS，弹药 ≥1。
- 允许对空射击（目标格没有敌人 → 空放，消耗 1 发子弹），可用于封锁"最后已知位置"。
- 命中率按距离分档，目标站在森林时再 **-20 个百分点**，下限 10%：

| 距离 d | 2 及以内 | 3~4 | 5~6 | 7~8 |
| --- | --- | --- | --- | --- |
| 基础命中率 | 90% | 70% | 50% | 30% |

- 伤害：命中 **20**（5 发击毁满血坦克）；目标在森林中 **10**（掩体减半）。HP ≤ 0 → 死亡。
- 无友军伤害（自由混战 FFA）：场上除自己外都是敌人。
- 命中判定由引擎用种子随机数结算，结果通过事件回执给射击者（`hit` / `miss`）。

**防御（`{type:"defend"}`）**
- 停止一整个回合举盾（占满 2 AP），从自己的回合立刻生效，**接下来 2 轮（含本轮）炮弹伤害被完全挡下**：打中了也照样消耗炮弹，但伤害为 0（引擎事件里带 `blocked` 标记，回放日志写"被防御弹开"）。
- 只挡炮弹：**踩到地雷照样清空血量**。
- **对手看不到你在防御**：脚本侧的 `state.enemies` 里没有任何防御字段，只有自己的 `state.self.defendLeft` 知道还剩几轮。对方唯一的察觉方式是"打中了但伤害是 0"。
- 重新防御会把计时重置回 2 轮；死亡会清掉防御（复活是裸车）。
- 观战/回放能看到防御状态（车外一圈蓝色护罩 + 座位卡上的「🛡 防御 N」标签）——这是"上帝视角比选手知道得多"的地方。

**地雷（`{type:"deployMine"}`）**
- 消耗 1 AP + 1 枚地雷，埋在**自己当前所在的格子**上；任何可通行格都可以埋，**森林里也算**（森林不改变地雷的可埋性与触发）。
- 随身上限 2 枚（`RULES.mineMax`，地图可覆盖）：开局与复活都是满的，之后只能在**弹药补给点**装弹时一起补满（`loadAmmo`，地雷不额外扣分，但吃该点库存）。
- **对所有人不可感知**：`state` 里没有任何"哪里有雷"的字段——包括你自己埋的雷，脚本只能靠自己的变量记（模块级变量在整场比赛里持续存在）。观战/回放看得到（红色引信的小圆盘）。
- **触发**：任何坦克**移动进入**该格时立刻引爆并消耗这枚雷，**踩中的坦克血量清空（直接阵亡）**，防御也挡不住；埋雷方按击杀记账（`+20` 分），自己踩自己的雷不算击杀（`killerSeat` 为 null）。
- 一枚雷只有一次机会：引爆即消耗，同一格可以叠放多枚（按埋下的先后顺序触发）。
- 复活/开局"出现在"格子上不算"移动进入"，所以出生点上即便有雷也不会一复活就炸。
- **它挡路时对埋雷方也一样挡**：地雷不分敌我，埋在自己必经的窄路/设施上等于把那条路对自己也封了——这是使用时最容易吃亏的地方。

## 6. 死亡、复活与惩罚

| 事件 | 结果 |
| --- | --- |
| 死亡 | **-20 分**（配置 `deathPenalty`），载货清零 |
| 停机 | 死亡后**跳过自己的 3 个回合**（配置 `respawnRounds`），期间脚本不会被调用 |
| 复活 | 在出生点复活：HP 100 / 弹药 6 / 燃油 40 / 载货 0，**免费** |
| 击杀奖励 | 击杀方 **+20 分**（配置 `killReward`，设为 0 即完全按"只有死亡扣分"的原始需求） |

注意：脚本在 `onTurn` 被调用时 `state.self.alive` 恒为 `true`（停机期间不调用），因此脚本只需处理"我还活着但可能残血少弹"的情况。

## 7. 计分与结算

**得分公式**

```
总分 = 10 × 已提交资源单位数
     + killReward × 击杀数          (默认 20)
     - deathPenalty × 死亡数         (默认 20)
     - 2 × 已装填炮弹数
     - ceil(累计加入燃油 / 10)       （按每次加油动作分别向上取整后求和）
```

分数**可以为负**。"补弹药、加油都从积分里扣"是核心经济约束：一次完整资源往返（提交 5 单位 = +50）大约要花 9 分燃油；打空一个弹匣（20 发 = 40 分）大约能造成 2~3 次击杀（期望值）。**地雷不扣分**（只在弹药点补满时占用库存与跑腿成本），所以它的代价是"行动力 + 一次机会 + 挡自己也挡别人"。

**排名**

1. 总分高者胜；
2. 平局 → 提交资源单位数多者胜；
3. 再平 → 击杀数多者胜；
4. 再平 → 死亡数少者胜；
5. 仍平 → 并列（排行榜按并列记录）。

**默认参数汇总（全部可配置，改动即升 ruleset 版本）**

> 表里是规则默认值。**地图还能再覆盖四项车辆上限**（`hpMax` / `ammoMax` / `cargoMax` / `mineMax`，见 §2.3）：脚本一律读运行时的 `state.self.*`，不要把这些默认值抄进代码。

| 参数 | 默认 | 参数 | 默认 |
| --- | --- | --- | --- |
| `maxRounds` | 150 | `apPerTurn` | 2 |
| `hpMax` | 100 | `ammoMax` | 20 |
| `fuelMax` | 100 | `cargoMax` | 5 |
| `moveFuelCost` | 2 | `fuelPricePer10` | 1 |
| `ammoPrice` | 2 | `loadAmmoPerAction` | 6 |
| `refuelPerAction` | 30 | `collectPerAction` | 3 |

## 8. 一局的完整流程（引擎视角）

1. 抽签座位 → 初始化地图资源点余量、坦克初始值、种子 RNG。
2. 对每个座位调用 `onInit(ctx)`（每次比赛只调用一次，可做路径预计算）。
3. 进入轮次循环 `r = 1..maxRounds`：
   1. 计算轮换后的行动顺序；
   2. 对每个"存活且不在停机期"的座位：计算视野 → 构造 `state` → 调用 `onTurn(state)` → 校验并依次执行动作（按动作扣 AP、结算移动与踩雷、伤害与防御）→ 广播事件；
   3. 结算死亡/复活计时、资源点回充、**补给点回充**、防御计时 -1、燃油/弹药扣费、事件日志；
   4. 若死够时长的座舱 → 复活（补满燃油/弹药/地雷，并清空防御）。
4. 达到 `maxRounds` → 结算分数、排名，输出战报与回放。

**确定性要求**：给定 `mapVersion + rulesetVersion + seed + 各座位脚本`，事件流必须逐字节可复现（用于回放与争议复盘）。脚本自身的随机必须走 `API.random()`（按座位独立种子流），禁止使用时间与系统随机。

## 9. 平衡性记录与调参口径

**验收口径**（用 `tools/cli` 跑仿真验证，不是拍脑袋）：
```bash
node --import tsx tools/cli/src/index.ts simulate --games 60 --seats 4               # 4 人局（默认 arena-01），看整体收益与离散度
node --import tsx tools/cli/src/index.ts simulate --games 200 --seats 2             # 1v1（默认 duel-01），看交战强度
node --import tsx tools/cli/src/index.ts simulate --games 20 --seats 2 --sandbox    # 沙箱路径（口径与正式比赛一致）
```

**ruleset-1.0 → 1.1 的实测依据**（基线脚本 v1、四方局、10~60 局）：

| 配置 | 全场均分 | 得分标准差 | 座均提交 | 座均死亡 | 中心策略 vs 守家策略 |
| --- | --- | --- | --- | --- | --- |
| 1.0（伤害 30、死亡 -30） | 5.8 | 105 | 10 单位 | 2.8 | **-4.6**（去中心反而亏） |
| 1.1（伤害 20、死亡 -20） | 74 | 89 | 17 单位 | 2.6 | **+43.5**（去中心明显更优） |

结论与调整：
1. **伤害 30 → 20**（由 4 发击毁变为 5 发）：这是决定性的一改。原先"敢去中心"是负收益（`-4.6`），因为一轮交火就分胜负、来不及脱离；改成 5 发击毁后交火有回旋余地，中心的效率优势（10 步换 50 分 vs 44 步）才真正体现为收益（`+43.5`），地图设计意图（高风险高收益的必争之地）成立。
2. **死亡扣分 30 → 20**：把"比谁死得少"的游戏改回"比谁采得多"。死亡仍是最重的单笔惩罚（约半趟资源收益）且有 3 回合停机。
3. **击杀奖励维持 20**：伤害降低后一次击杀的弹药成本（约 10 发 = 20 分）与奖励基本持平，所以击杀是"战术手段（清场、护货）"而不是"刷分手段"，符合设计意图。
4. **地图 arena-01@2**：在中心广场两侧各加 2 个加油点。原因是 1.0 版的中心区"离补给太远"——去中心采集后必须横穿半张图回四角加油，一趟的实际步数与近端资源点相同，却要多承担交战风险，于是**去中心严格劣于守家**。加了中心加油点后，中心可以连续往返刷分，风险才换来收益。
5. **离散度仍然很大（标准差 ≈ 89~100）是 FFA 的固有特性**，不是座位偏置：已验证 60 局中每个座位的出生点分配均匀（每格约 15 次）。含义是——**单个对局的胜负不能代表模型强弱**，排行榜应按多局均值/胜率统计（前端的排行榜与 ELO 都以此为口径）。

调参建议（改数值必须同时改 `packages/protocol/src/rules.ts`、`docs/02` 与本表，并升 ruleset 版本；`tools/cli check-docs` 会卡住漂移）：
- 想让交火更频繁：把 `fireRange` 提到 10 或 `hitChanceBands` 上调。
- 想削弱"龟缩守家"：提高 `depositScorePerUnit` 的中心区收益（例如给中心资源点更高的 `capacity`），或缩短 `maxRounds` 让慢速流派来不及回本。
- 想让燃油物流更吃紧：提高 `moveFuelCost` 或降低 `refuelPerAction`。

### 9.1 基线脚本 v2 与 duel-01 复测（2026-10-19）

**为什么要改基线**：v1 基线的目标选择里有一条 `self.hp < 60 就不去中心`，而本游戏**没有任何回血手段**——一旦残血就永远残血，于是 v1 在被打一次之后就永久退守角落。在 arena-01 上这只表现为收益偏低（近端资源点还够它循环），但在 duel-01 上会直接演变成"双方各自蹲在角落等资源点每 8 回合回 1 单位"的死局（实测 1v1 前 8 回合交火、之后 140 回合无战事，中央资源点空闲 100+ 回合）。基线是所有外部 Agent 的参考实现，这种"示范性苟活"必须修掉。

**v2 相对 v1 的四处改动**（都在 `docs/examples/baseline-strategy.js`）：
1. **取消"残血退守"**：残血继续争夺（阵亡只扣 20 分、3 回合后满血复活，比拖着一个永远残血的身子守家更划算）。
2. **采空的资源点立刻换目标**，不再原地等回充。
3. **站上设施时把 2 点行动力用满**（一次采集两下装满货舱、一次补满油/弹），少一次来回。
4. **开火加入弹药价值判断**：近距（≤4）/ 残血 / 载货的敌人值得打，远距满血敌人只在弹药宽裕（≥9 发）时打——4 人局里弹药是最容易被浪费的支出。

**A/B 实测（新基线 vs 旧基线各占一半座位，80 局）**：

| 场景 | 旧基线 | 新基线 | Δ |
| --- | --- | --- | --- |
| arena-01 四方（人均分） | 60.4 | 62.6 | **+2.2** |
| arena-01 1v1（人均分） | 156.8 | 186.5 | **+29.7** |
| duel-01 1v1（人均分） | 89.3 | 519.6 | **+430.3** |

结论：新基线在大图不弱于旧版（4 人局持平、1v1 更好），在小图上把"本来该拿的分"拿到了。

**duel-01 的验收数据**（新基线，`simulate`）：

| 指标 | duel-01（1v1，200 局） | arena-01（4 人，60 局） |
| --- | --- | --- |
| 发生交火的对局 | **200/200** | 60/60 |
| 首次交火平均轮次 | **第 4 轮** | 第 10 轮 |
| 场均开火 / 命中 / 击杀 | 85.7 / 67.7 / 12.5 | 138.7 / 92.8 / 17.6 |
| 座均得分（标准差） | 247.0（121.2） | 43.1（97.8） |
| 座均死亡 | 6.2 | 4.4 |
| 中心策略 vs 守家策略 | **265.4 vs 122.9（Δ+142.5）** | 11.6 vs 3.6（Δ+8.0） |
| 沙箱路径单局耗时 | 42ms（本地 1ms） | — |

要点：
1. **1v1 的交战强度是这张图的验收指标**：200/200 局都在第 4 轮前后爆发接触，场均有 12.5 次击杀（arena-01 是 17.6 次/4 座 = 人均 4.4 次，duel-01 人均 6.25 次）。
2. **守家在 duel-01 上是被明确惩罚的**（Δ+142.5，差距远大于 arena-01 的 +8.0），因为全图只有一个提交点且它在正中央：不进去就等于不拿分。
3. **单局胜负不可作为强弱依据**：同一脚本的 200 局镜像对局里，座位均分差异在两次独立测量中符号相反（P1 232.2 vs P2 261.9 / P1 177.5 vs P2 152.3），说明差异来自逐座位随机流导致的混沌，而不是座位或出生点偏置。排行榜按多局统计（见 docs/05 的赛制）。
4. 沙箱（正式比赛口径）与本地的结论一致，只慢约 40 倍（42ms/局，仍远低于 50ms/回合的决策预算）。

### 9.2 ruleset-1.2（防御 + 地雷）与基线脚本 v3 复测（2026-10-20）

**1.2 加了两条动作**：`defend`（停止一回合举盾，2 轮内炮弹伤害全免、对手不可感知）与 `deployMine`（埋雷，不分敌我、对所有人不可见，踩中即清空血量）。数值层面只多了两个参数：`defendRounds: 2`、`mineMax: 2`（地雷在弹药点装弹时免费补满，吃同一份库存）。

**基线 v3 相对 v2 的三处改动**（都在 `docs/examples/baseline-strategy.js`）：
1. **会举盾**：一炮就能被打死、且对手刚刚开过火（或已贴到身边）时，整回合举盾；带 6 轮冷却，防止一路龟缩把收入耗光。
2. **会顺手布雷**：被对手贴到 2 格以内、脚下是开阔地（四邻至少 3 格可走）且不是设施格时，在脚下留一颗雷再撤；带 8 轮冷却。
3. **会记自己的雷**：地雷对自己也不可见，基线用模块级变量记下埋过的位置，寻路时把自己埋的雷当作障碍**绕行**（原位放弃目标的写法实测会把车卡死），并在公告里看到"自己的雷被踩响"后划掉记录。

**实测（`simulate`，本地执行，ruleset-1.2，maxRounds 120）**：

| 指标 | duel-01（1v1，60 局） | arena-01（4 人，40 局） |
| --- | --- | --- |
| 座均分 | **154.5** | **-3.8**（同一基线关掉地雷时为 **+36.6**） |
| 座均死亡 | 5.7（关雷时 4.7） | 3.8（关雷时 3.0） |
| 座均布雷 / 其中被对手踩响 | 5.1 / 2.3 | 2.7 / 1.3 |
| 触发地雷次数/局 | 4.6 | 5.3 |
| 举盾次数/局 | 5.6 | 9.4 |
| 踩到自己埋的雷/局 | **0.00** | **0.00** |

结论与调参口径：
1. **地雷的净代价是"交易性损耗"**：一枚雷炸响 = 对方 -20 分 + 掉货 + 停机 3 回合，而自己只拿到 +20 与一段清场时间 —— 双方都布雷时，两个人的收入一起掉。4 人局的座均分从 +36.6 掉到 -3.8 就是这么来的，**不是引擎或基线出的错，而是"互相拆台"的机制在四人局里被放大了**。
2. **想回到纯经济局**：把地图的 `mineMax` 写 0（编辑器里「最大地雷 0」，`ammoMax: 0` + `mineMax: 0` 才是真的没有战斗），或把基线里的 `MINE_COOLDOWN` 调成大数。
3. **举盾是"低血量 + 挨过打"才触发的**：4 人局 9.4 次/局、1v1 5.6 次/局，都属于"被逼到墙角"的偶发行为，没有变成龟缩流。
4. **"自己埋的雷不能自己踩"是这版基线的硬指标**：200 局里 0 次自炸（关掉记忆或绕行逻辑都会立刻打回原形）。
5. **确定性、无效动作、strike 全部不受影响**：无效动作 0.1 次/座，strike 0，事件流仍逐字节可复现（同一 seed 的回归用例在 `packages/engine/test`）。
